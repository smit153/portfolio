Type "rename this variable" as the 8th message of a Claude Code session. Then type exactly the same thing as the 80th. Same words, same answer, and with my sample numbers the second one costs about three times as much. Turn prompt caching off and it's six times.

Nothing is broken. A long session hits a quadratic curve twice: inside the model, where attention compares every token with every earlier one, and on your bill, where every turn sends the whole conversation again. Caching makes the repeat cheaper but doesn't change the shape of either curve. There's a simulator at the end.

## The model forgets everything between requests

Claude Code's docs say it plainly: "The model doesn't remember anything between requests, so Claude Code re-sends the full context." One message from you is rarely one request, either. Every tool call sends its result back as another request carrying everything before it, so a long session is a series of requests, each a bit bigger than the last.

## What attention actually computes

A token is a chunk of text, roughly ¾ of an English word. Inside a transformer it becomes a vector of a few thousand numbers, and attention is the step where tokens look at each other. It's how "it" works out which noun it points to.

Each token gets three vectors:

- **Query (Q)**: what this token is looking for.
- **Key (K)**: what this token offers to others.
- **Value (V)**: the information it passes on if someone attends to it.

A token's query is compared with every key using a dot product (multiply two vectors element by element and add it up). A high score means "relevant to me". Softmax turns the scores into weights that add up to 1, and the output is the weighted sum of the values. The original paper writes it in one line:

<div class="formula">Attention(Q, K, V) = softmax( Q·Kᵀ / √d<sub>k</sub> ) · V</div>

The √d<sub>k</sub> just keeps the scores from getting so big that softmax can't cope.

## Every token checks every earlier token, so the work is n²

Q·Kᵀ is every query against every key: with n tokens, an n × n grid of dot products. The paper lists self-attention at **O(n²·d)** per layer. (O-notation means "grows like": double n and the work grows four times.) Language models add one rule: a token can only look backwards. That causal mask cuts the grid to a triangle of about n²/2 cells, which still grows like a square.

<AttentionGrid />

At 1,000 tokens the triangle has about half a million cells. At 100,000, normal for a coding session that has read a few files, about five billion. At 1 million, the full context window on current Claude models, about 500 billion, per head, per layer. FlashAttention fixed the memory half by never storing the whole grid, but it still computes every cell, so the time stays quadratic.

## The KV cache makes each new token linear, not the whole reply

A reply is written one token at a time. The key and value vectors of old tokens never change when a new token arrives, so the server keeps them in GPU memory instead of rerunning the whole sequence. kipply's write-up says the point is "to avoid recalculations of those vectors every time we sample a token."

Some explainers get this wrong: the KV cache doesn't make generation linear. Each new token still does one dot product per earlier token, so the total over a reply is still about n²/2. What the cache removes is the re-run, which would make generation closer to cubic.

The two phases have names. **Prefill** processes your whole prompt at once, the full triangle. **Decode** adds one row at a time. Sebastian Raschka: decoding work per new token "grows linearly with the retained prefix."

## How much of the work is attention, really

Attention isn't the only work in a transformer. Every token also goes through the big weight matrices, and that part doesn't depend on context length. By Kaplan et al.'s approximation (forward cost per token is about `2N + 2·n_layer·n_ctx·d_attn`), the two parts are equal at about 12 × d_model tokens.

<AttentionShare />

With a width of 8,192, attention is a rounding error in a 2,000-token chat. At 1M tokens it's about 91% of the compute, and each token costs about 11 times what it would in an empty context.

Yet you pay a flat price: Anthropic says a 900k-token request "is billed at the same per-token rate as a 9k-token request." So the curve on your bill comes from somewhere else.

## Your bill is quadratic for a different reason

Say a session starts with S tokens (system prompt, tools, CLAUDE.md) and each turn adds about a tokens. Turn k sends roughly S + k·a tokens, so K turns add up to about S·K + a·K²/2. The second term grows with the square of the session length. It's the same triangle: each turn is a row, and each row re-sends everything above it.

## Prompt caching lowers the slope, not the shape

If the start of a request (the prefix) exactly matches something processed recently, the API skips the recompute and bills that part at a much lower rate. Anthropic doesn't say what it stores. The open-source vLLM server does "cache the kv-cache blocks of processed requests", so I'd guess it's the KV cache from Demo 2, kept between requests.

A 5-minute write costs 1.25× the input price and a 1-hour write 2×. A read costs 0.1× (0.05× on Opus 5.5 and Sonnet 5.5) and resets the timer for free. Claude Code sets this up for you.

A 10× or 20× discount sounds like it fixes everything, but the cached part is the part that grows. Each turn still re-reads the whole history at a fraction of the price, and a fraction of a quadratic is still a quadratic. Thinking tokens, which are billed as output, add a flat cost per turn on top.

The timer matters more than you'd think, and it runs from the start of a request, so a long generation eats into it. Claude Code's docs say the lifetime is an hour on a subscription but five minutes on an API key or once you're on usage credits. Step away for coffee on an API key and the next message rewrites the whole context at the write price.

With the defaults (Sonnet 5.5, a 20k-token start, 3k tokens added per message, four requests per message) message 8 costs about $0.05 and message 80 about $0.16. The 80-message session comes to about $8.10, or about $112 without caching. Cache reads are around two-thirds of the cached bill: the re-sending, at a discount.

## What actually moves the curve

Try these in the simulator. Each matches Anthropic's docs.

- **/clear resets the triangle.** A /clear at message 41 cuts the default session from about $8.10 to about $5.70. The system prompt and tools are still the same prefix, so they stay cached.
- **/compact is a big request itself.** It reads the whole conversation to write the summary, so it saves about as much as /clear but costs one large read first. Worth it when you need the continuity.
- **A break longer than the cache lifetime hurts most late in a session.** A 20-minute break before message 60 on the 5-minute cache takes that one message from about $0.13 to about $0.72, because the whole context gets written again. At message 5 you'd barely notice.
- **The 1-hour cache isn't free.** Writes cost 2× instead of 1.25×, so with no long breaks the default session gets slightly more expensive ($8.60 against $8.10). It pays off when you step away for more than five minutes.
- **Switching models throws the cache away.** Each model has its own cache. Connecting an MCP server whose tools load up front does it too, and on most models so does changing effort mid-session.
- **Subagents start their own context.** They don't read the parent's cache and get the 5-minute lifetime by default, but their verbose output stays out of your main conversation, so it isn't re-sent on every later message.

## What this model can't tell you

- **It's not your bill.** Real sessions are uneven, and the simulator spreads tokens evenly. Run `/usage` for real numbers. Recent versions show a `Prompt cache (main)` line with your hit rate and misses.
- **Subscriptions don't bill per token.** On Pro or Max you hit usage limits, not a dollar figure, but the same curve decides how fast.
- **The attention numbers are textbook, not Claude.** Anthropic doesn't publish its architecture, and tricks like grouped KV heads or sliding windows change the constants. The O(n²) shape holds for standard full attention.
- **What's in the cache is a guess.** Anthropic's docs describe caching by prefix, not by mechanism. The KV-cache story comes from open-source servers.
- **Long context has a quality cost too.** Whether the model uses message 3 well at message 80 is a separate question I haven't covered.

## What I'd actually do

I'd treat a session like a branch, not a home: one task per session, and /clear when the task changes. Keep CLAUDE.md short, since it's in every request (Anthropic suggests under 200 lines). Pick the model and effort at the start and leave them alone. If you're on an API key and tend to wander off mid-task, set `promptCacheTtl` to `1h` or run /compact before you leave. When a test run or log dump will be huge, let a subagent read it and hand back the summary.

None of that changes the shape. It just keeps you on the cheap end of the curve.
