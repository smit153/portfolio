Every new table raises the same question: how do you identify a row? Most of us answer with habit, an auto-increment integer because it's right there or a UUID because someone said integers don't scale. Both cost you something. UUIDv7 is the first option I've found that doesn't make me pick.

## Auto-increment is cheap, until you need more than one writer

An auto-increment column is the default for good reason. Every engine ships it: `AUTO_INCREMENT` in MySQL, `GENERATED ... AS IDENTITY` (or the older `SERIAL`) in Postgres, `IDENTITY` in SQL Server. It's compact (four bytes for an `int`, eight for a `bigint`), reads fine in a URL (`orders/1042`) and is easy on the index.

The trouble comes later: the next number has to come from one authority, so once two servers insert at the same time they have to coordinate or they'll both hand out `1043`.

The values are guessable too. From `/users/42`, `/users/43` is the obvious next try. If the app doesn't check you may see user 43, that's an IDOR (insecure direct object reference): reaching records that aren't yours by editing an ID in a URL.

## UUIDv4 solves both problems and breaks your index

A random UUID (version 4) is 122 bits of randomness with the version and variant bits stamped on top. Any process can generate one without asking anyone, and nobody can walk your table by adding one. That fixes both problems.

The bill comes due in the index. A primary key lives in a B-tree, which keeps entries sorted across fixed-size pages. With a sequential key, each insert is larger than the last, so it lands at the right edge, fills the page and starts a new one.

A v4 lands wherever it sorts, usually in a full page. The database splits it: allocate a new page, copy half the rows, update the parent. Splits cost CPU and I/O and fragment the index, so reads touch more pages. A UUID is also 16 bytes, four times an `int` and twice a `bigint`, so the index is bigger and less of it fits in memory.

## What v7 changes

v7 keeps the 128-bit shape and rearranges the bits. The first 48 bits are a Unix timestamp in milliseconds, then a 4-bit version, a 2-bit variant and random bits. That's RFC 9562, the 2024 standard that replaced RFC 4122.

<Layout />

With the clock in front, a later v7 sorts after an earlier one, and RFC 9562 says databases can sort it as plain raw bytes. Version 1 also had a timestamp, but stored it in an order that doesn't sort by time. A v7 appends to the right edge of the tree like a sequential integer, while the random tail keeps it unique and lets any node mint one on its own.

## What v7 can't do

A v7 is still 16 bytes, twice a `bigint`, and you still can't read one aloud over the phone.

The timestamp is also in the open. Anyone holding a v7 can decode roughly when the row was created and how fast you issue IDs. Demo 2 does it in a few lines, and Postgres ships `uuid_extract_timestamp()`, whose docs warn the result may not equal the exact creation time.

You get fewer random bits than v4, too: 74 against 122. That's plenty to avoid collisions and stop enumeration, but it's a ceiling: RFC 9562 lets generators spend some on a counter or extra time precision, and Postgres' `uuidv7()` puts sub-millisecond time there. So I wouldn't use a v7 for anything meant to stay secret, and the RFC says UUIDs must not be used as security capabilities. For reset links, session tokens and invite codes, use a v4 or a proper random token. Keep v7 for primary keys and log IDs, where the creation time isn't sensitive.

Last limit: with several writers, order is only as good as their clocks. Servers a few milliseconds apart produce IDs that are roughly sorted, not strictly. That's fine for an index, but if you need strict global order, v7 alone won't give it.

## What I'd reach for

On a single node where IDs never leave the database, auto-increment is still the leanest option. Don't pay 8 bytes for problems you don't have.

With more than one writer, or an ID in a URL or API response, skip v4 and use v7. You keep decentralized generation and unguessability without handing your index busywork.

<Chooser />

Adopting v7 is nearly a one-liner now. Postgres 18, out in September 2025, ships a built-in `uuidv7()`:

```sql
CREATE TABLE orders (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  placed_at timestamptz NOT NULL DEFAULT now()
);

SELECT uuid_extract_timestamp(id) FROM orders LIMIT 1;
```

On older Postgres, generate the value in your app. MySQL's `UUID()` makes version 1, so generate v7 client-side and store it as `BINARY(16)`. Hibernate 7 has a `VERSION_7` UUID generator style and .NET 9 has `Guid.CreateVersion7()`. Check your ORM for the equivalent.
