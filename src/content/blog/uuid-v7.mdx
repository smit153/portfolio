Every new table asks the same question: how do you identify a row? Most of us answer on autopilot. An auto-increment integer, because it's right there. Or a UUID, because someone once said integers don't scale. Both send you a bill later. UUIDv7 is the first option I've found that doesn't make me pick.

## Auto-increment is great, until there are two of you

Every engine ships one, whether it's `AUTO_INCREMENT` in MySQL, `GENERATED ... AS IDENTITY` in Postgres or `IDENTITY` in SQL Server, and it's tiny: four bytes for an `int`, eight for a `bigint`, perfectly fine in a URL like `orders/1042`. Your index loves it.

The catch? The next number has to come from one place, so the moment two servers are inserting at once they either coordinate or they both hand out `1043`.

It's also guessable. If you're `/users/42`, you can probably guess where `/users/43` lives, and if the app forgets to check, you're in. That's an IDOR (insecure direct object reference), and it's exactly as embarrassing as it sounds.

## UUIDv4 fixes both and quietly wrecks your index

A v4 is 122 random bits with the version and variant stamped on top. Any process can mint one without asking anyone, and nobody's walking your table by adding one.

The bill arrives in the index. A primary key lives in a B-tree, which keeps entries sorted across fixed-size pages. Sequential keys always land at the right edge: fill a page, start the next one, very tidy. A v4 lands wherever it sorts, usually in a page that's already full, so the database splits it. Every time. New page, copy half the rows over, update the parent. That costs CPU and I/O, fragments the index, and makes reads touch more pages. And at 16 bytes, a UUID is four times an `int`, so less of the index fits in memory.

## What v7 changes

v7 keeps the 128-bit shape and just reorders it. The first 48 bits are a Unix timestamp in milliseconds, then the version and variant bits, then randomness. That's RFC 9562, the 2024 standard that replaced RFC 4122.

<Layout />

Clock in front means a later v7 sorts after an earlier one, as plain bytes. (Version 1 had a timestamp too, but stored it in an order that doesn't sort by time. Classic.) So v7 appends to the right edge of the tree like an integer, while the random tail keeps it unique and lets any node make one on its own.

## What v7 can't do

It's still 16 bytes. Try reading one out over the phone.

The timestamp is out in the open, too. Anyone holding a v7 can tell roughly when the row was created and how fast you're issuing IDs. Demo 2 does it in a few lines, and Postgres ships `uuid_extract_timestamp()` for exactly this.

It also has fewer random bits than v4 (74 against 122). That's plenty for avoiding collisions, but the RFC says UUIDs must not be used as security capabilities, and I'd take that personally. Reset links, session tokens, invite codes: use a v4 or a proper random token. Keep v7 for primary keys and log IDs.

Last one: with several writers, order is only as good as their clocks, and servers a few milliseconds apart will give you IDs that are roughly sorted rather than strictly sorted. Your index won't care. If you need strict global order, v7 alone won't get you there.

## What I'd reach for

One database and IDs that never leave it? Auto-increment is still the leanest thing going. Don't pay 8 extra bytes for problems you don't have.

More than one writer, or an ID that shows up in a URL or an API response? Skip v4 and use v7. You keep decentralised generation and unguessable IDs without making your index do busywork.

<Chooser />

Adopting it is nearly a one-liner now. Postgres 18 (September 2025) ships a built-in `uuidv7()`:

```sql
CREATE TABLE orders (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  placed_at timestamptz NOT NULL DEFAULT now()
);

SELECT uuid_extract_timestamp(id) FROM orders LIMIT 1;
```

On older Postgres, generate it in your app. MySQL's `UUID()` makes version 1, so generate v7 client-side and store it as `BINARY(16)`. Hibernate 7 has a `VERSION_7` generator style and .NET 9 has `Guid.CreateVersion7()`.
